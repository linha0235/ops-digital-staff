# 运维数字员工系统——课程报告设计书

## 1、引言

### 1.1 项目背景

随着企业 IT 基础设施规模的不断扩大，运维团队面临日益增长的工单处理压力。传统运维模式依赖人工记忆和经验，存在以下痛点：

- **知识散落**：运维经验分散在个人头脑中，人员流动导致知识流失
- **重复劳动**：80% 的工单为常见问题，运维人员反复回答相同问题
- **响应延迟**：非工作时间无法及时响应用户报障
- **经验难复用**：处理完成的工单缺乏结构化沉淀机制

基于大语言模型（LLM）和检索增强生成（RAG）技术，本项目构建了一套智能运维助手系统，通过私有化部署的大模型和本地知识库，实现 7×24 小时智能问答，将运维人员从重复性工作中解放出来。

### 1.2 项目目的

1. **构建运维私有知识库**：将运维经验结构化为 FAQ 问答对，支持语义检索
2. **实现智能问答**：基于 RAG 技术，用户用自然语言提问，系统自动匹配知识库或调用大模型推理
3. **工单闭环管理**：从报障、受理、处理到回访的全流程数字化
4. **本地化部署**：所有数据和模型运行在本地，保障数据安全

### 1.3 项目特色

| 特色 | 说明 |
|------|------|
| 🏠 完全本地化 | 大模型和数据均在本地运行，数据不出域 |
| 🔍 本地嵌入 RAG | 基于 bge-m3 的语义搜索，不依赖外部向量数据库 |
| 🛡️ 三层回退 | 本地嵌入 → AnythingLLM → Ollama 直连，层层降级保可用 |
| ⚡ 流式输出 | SSE token 级流式推送 + 打字机动画，交互体验流畅 |
| 🔧 配置外置 | 模型名、超时、阈值等可配置，无需改代码 |
| 🚫 安全校验 | 密码不返回前端、输入参数严格校验、异常不泄露内部信息 |

### 1.4 项目风险

| 风险 | 等级 | 应对措施 |
|------|------|----------|
| 大模型响应延迟 | 中 | 本地嵌入优先匹配（< 200ms），避免每次都调用大模型 |
| 知识库覆盖不足 | 中 | 工单闭环：处理完成的问题自动沉淀到知识库 |
| Ollama 服务不可用 | 低 | 友好降级，返回明确错误提示 |
| 嵌入模型精度不足 | 低 | 阈值可配置，0.75 经实测验证效果良好 |
| 并发性能瓶颈 | 低 | 线程池管理（4 核心 / 16 最大），支持横向扩展 |

### 1.5 产品范围

**包含**：
- 运维人员账号管理（增删改查、冻结/解冻）
- 知识库管理（FAQ CRUD、启用/停用、向量同步）
- 智能问答（RAG 流式对话、知识库语义匹配）
- 工单管理（创建、受理、处理、回访、满意度）
- 首页仪表盘（数据统计概览）

**不包含**：
- 移动端 App（仅 Web 端）
- 多租户支持
- 单点登录（SSO）
- 邮件/短信通知

## 2、综合描述

### 2.1 用户类和特性

| 用户角色 | 职责 | 核心功能 |
|----------|------|----------|
| 普通运维人员 | 处理工单、查阅知识库 | 工单处理、智能问答、知识库搜索 |
| 系统管理员 | 系统管理、用户管理 | 账号管理、知识库维护、工单分配 |
| 普通用户（报障人） | 提交工单、自助查询 | 智能问答、工单提交 |

### 2.2 运行环境

**开发环境**：

| 组件 | 版本/配置 |
|------|-----------|
| JDK | OpenJDK 17.0.15 |
| Maven | 3.9.9 |
| Node.js | 24.15.0 |
| MySQL | 8.0.31 |
| Redis | 7.2 |
| Ollama | 0.30.4 |
| 操作系统 | Windows 11 |

**生产环境建议**：

| 组件 | 最低配置 | 推荐配置 |
|------|----------|----------|
| CPU | 4 核 | 8 核 |
| 内存 | 8 GB | 16 GB |
| 硬盘 | 100 GB | 500 GB SSD |
| GPU | 无（CPU 推理） | NVIDIA 8GB+ VRAM |

### 2.3 设计和实现上的限制

1. **通信协议**：前后端通信采用 HTTP/HTTPS + SSE，不支持 WebSocket
2. **会话管理**：当前为单用户模式，无登录鉴权（后续可扩展 JWT）
3. **大模型**：依赖本地 Ollama 服务，qwen2.5:3b 为当前最优性价比选择
4. **嵌入模型**：bge-m3 嵌入维度 1024，向量缓存在 JVM 内存中
5. **前端路由**：使用 HTML5 History 模式，生产环境需 Nginx 配置 fallback

### 2.4 假设和约束（依赖）

| 依赖项 | 说明 |
|--------|------|
| Ollama 服务 | 必须运行在可访问的地址，默认 localhost:11434 |
| MySQL 数据库 | 存储业务数据，默认端口 3306 |
| Redis | 缓存（当前未深度使用，预留），默认端口 6379 |
| AnythingLLM | 可选，不安装也能正常使用 |

## 4、非功能需求分析

### 4.1 性能需求

| 指标 | 目标值 | 实测值 |
|------|--------|--------|
| 知识库匹配响应时间 | < 500ms | < 200ms |
| 流式问答首字响应 | < 3s | 1.64s |
| 非流式问答总时间 | < 30s | < 10s |
| 页面首次加载 | < 3s | < 2s |
| 并发问答支持 | 10 并发 | 4-16（取决于线程池） |

### 4.2 可靠性需求

- **服务可用性**：≥ 99%（核心依赖 Ollama 和 MySQL 均本地部署）
- **故障恢复**：Spring Boot 崩溃后自动重启
- **降级策略**：本地嵌入失败 → Ollama 直连，任何单点故障不影响基本问答

### 4.3 安全性需求

| 措施 | 说明 |
|------|------|
| 密码加密 | BCrypt 哈希，不可逆 |
| 密码不泄露 | API 序列化为 WRITE_ONLY，响应中不含密码 |
| 输入校验 | 用户名唯一性、满意度 1-5 范围、空参数保护 |
| 异常信息 | 生产环境不暴露内部错误详情，返回通用消息 |
| CORS | 可配置允许来源，避免全开放 |
| SQL 注入 | MyBatis-Plus 参数化查询，天然防注入 |

### 4.4 可维护性需求

- **分层架构**：Controller → Service → Mapper 清晰分层
- **配置外置**：Ollama 地址、模型名、阈值等在 yml 中统一管理
- **代码规范**：Lombok 减少模板代码，统一 import 风格
- **接口文档**：Knife4j 自动生成 Swagger 文档

### 4.5 可扩展性需求

- **模型可替换**：修改配置即可切换 Ollama 模型（qwen2.5:3b → 7b → 14b）
- **嵌入模型可替换**：bge-m3 → bge-large 等
- **向量库可扩展**：当前内存缓存，可扩展至 Milvus/Pinecone
- **微服务拆分**：问答模块可独立为微服务

### 4.6 数据一致性

- 知识库 CRUD 操作后**即时**更新嵌入向量缓存
- FAQ 停用/启用**即时**从 AI 知识库生效
- 工单状态流转保证事务一致性（MyBatis-Plus 内置事务支持）
